# CardioFlow

Система сопровождения пациентов с сердечно-сосудистыми заболеваниями: пациент пишет в чат, ИИ-агент разбирает
реплику, бэкенд считает риск детерминированным движком и запускает эскалацию, интерфейс получает события в реальном времени.

```
┌──────────────┐  /api, /ws   ┌──────────────┐   POST /api/v1/agent/process   ┌──────────────┐
│  frontend    │─────────────▶│   backend    │───────────────────────────────▶│    agent     │
│ React + nginx│◀─────────────│   FastAPI    │◀───────────────────────────────│  LangGraph   │
│  :3000       │  WebSocket   │   :8000      │   Tool Calling (REST, JWT)     │   :8001      │
└──────────────┘              └──────┬───────┘                                └──────────────┘
                                     │
                              ┌──────▼───────┐
                              │ PostgreSQL 16│
                              └──────────────┘
```

| Папка | Что внутри |
|---|---|
| `frontend/` | React 18 + Vite + Redux Toolkit. Главная, чат, лечение (расписание), окно записи к врачу. Раздается nginx, который проксирует `/api` и `/ws` на бэкенд |
| `backend/` | FastAPI + SQLAlchemy (async) + PostgreSQL: REST, WebSocket, JWT, риск-движок, воркер эскалации (APScheduler) |
| `agent/` | FastAPI + LangGraph: разбор реплик (правила или LLM), вызовы API бэкенда, RAG по папке `knowledge/` |

## Запуск

Нужны Docker и Docker Compose v2.

```bash
unzip cardioflow.zip && cd cardioflow
docker compose up --build
```

Первая сборка занимает несколько минут (скачиваются образы и зависимости). Когда в логах появится
`Application startup complete` у backend, откройте:

| Адрес | Что это |
|---|---|
| http://localhost:3000 | Приложение (фронтенд) |
| http://localhost:8000/docs | Swagger бэкенда |
| http://localhost:8001/docs | Swagger агента |

Остановить: `Ctrl+C`, затем `docker compose down` (добавьте `-v`, чтобы удалить и данные БД).

Если порты заняты, задайте другие: `FRONTEND_PORT=3100 BACKEND_PORT=8100 docker compose up --build`
(полный список переменных в `.env.example`).

## Что посмотреть (сценарий демонстрации)

Демо-пациент «Иванов Иван Иванович» создается автоматически, вход не требуется: фронтенд сам получает JWT.

1. **Чат** (`/chat`): агент здоровается и пересказывает назначения врача, полученные с бэкенда (`GET /patient/treatment-plan`).
2. Напишите: `Давление 120/80, пульс 70`. Агент вызывает `POST /reports/`, бэкенд сохраняет замер,
   оценивает риск `stable`; на **Главной** обновляются показатели.
3. Напишите: `Давление 170/105, пульс 90, таблетку не принял, тошнит`. Риск `critical`, бэкенд шлет событие
   `show_appointment_slots`: открывается **окно записи** со свободными слотами, а агент пишет те же слоты в чат.
   Нажмите «Записаться»: слот бронируется (повторная бронь того же слота вернет 409).
4. Напишите: `Давление 150/95` (риск `warning`): агент просит повторить измерение, окно записи не открывается.
5. Спросите: `Сколько соли можно при гипертонии?`: ответ берется из базы знаний `agent/knowledge/` (RAG).
6. **Лечение** (`/treatment`): измените время приема. Интервал меньше 8 или больше 12 часов бэкенд отклонит (400).

Быстрые ответы-кнопки в чате (`Принял(а) лекарство`, `Плохо себя чувствую` и т.п.) тоже обрабатываются агентом.

## Автоматическая проверка связки

```bash
docker compose exec backend python scripts/e2e_check.py
```

Скрипт проходит тот же путь, что и интерфейс (JWT, WebSocket, приветствие агента, критический и нормальный замер,
RAG, запись в БД) и выводит `[OK]` / `[FAIL]` по каждому шагу. Тесты агента: `docker compose run --rm agent pytest -q`.
Проверка одного бэкенда: `docker compose exec backend python scripts/smoke_test.py`.

## LLM для агента (необязательно)

По умолчанию `LLM_API_KEY` пуст: агент разбирает реплики по правилам (давление, пульс, принял/пропустил, жалобы) и
не обращается во внешние сервисы. Чтобы включить LLM, создайте `.env` рядом с `docker-compose.yml`:

```env
LLM_API_KEY=ваш_ключ
LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_MODEL_NAME=модель_с_поддержкой_structured_output
```

и перезапустите `docker compose up -d --build agent`. Клинический риск в любом режиме считает только бэкенд.

## Как устроено взаимодействие

- **Фронтенд -> бэкенд**: `POST /api/v1/auth/token` (dev-выдача JWT по `patient_id`), затем REST с `Authorization: Bearer`
  и одно WebSocket-соединение `/ws/patient/{id}?token=...`. Токен обновляется автоматически (живет 30 минут).
- **Бэкенд -> агент**: реплика из сокета уходит в `POST /api/v1/agent/process` (`{patient_id, text, event_type}`),
  JWT пациента передается в `Authorization`. Ответ агента транслируется в сокет событием `agent_message`.
- **Агент -> бэкенд** (Tool Calling): `GET /patient/treatment-plan`, `POST /reports/`, `GET /slots/available` с тем же JWT.
- **Бэкенд -> фронтенд** (WebSocket): `agent_message`, `new_measurement_status`, `show_appointment_slots`, `patient_status_update`.
- Воркер эскалации (напоминание через 2 часа, итог дня в 22:00, потеря контакта) работает внутри бэкенда и шлет сообщения в тот же сокет.

## Что исправлено при объединении

Три проекта были написаны по отдельности и не стыковались. Основные правки:

- **Агент <-> бэкенд**: бэкенд вызывал `/api/v1/agent/process` с `{text}` и ждал `{text}`, а агент слушал `/process`, требовал
  `{jwt_token, message}` и отвечал `{reply_text}`. Теперь агент принимает оба формата, JWT берет из заголовка и отвечает обоими полями.
- **Токен для агента**: токен из URL сокета протухал через 30 минут при живом соединении; теперь для агента выпускается свежий.
- **Фронтенд -> бэкенд**: JWT нигде не получался (`localStorage` всегда пуст), а WebSocket был жестко `wss://`.
  Добавлены автоматическое получение и обновление токена, `ws://`/`wss://` по протоколу страницы, прокси в nginx и в dev-сервере Vite.
- **События WebSocket**: фронтенд открывал сокет только на странице чата, а события окна записи и замеров не обрабатывал никто
  (подписка `chatStream` нигде не вызывалась). Теперь одно соединение на все приложение, состояние в Redux, переподключение с задержкой.
- **Агент**: приём таблетки по умолчанию считался принятым (`medication_taken: true`), даже если о ней не писали;
  «мне 65 лет, пульс 70» разбиралось как давление 65/70; любая жалоба «плохо» без пропуска таблетки запускала запись к врачу.
  Исправлено, добавлена проверка диапазонов, чтобы бэкенд не отвечал 422.
- **RAG**: ChromaDB при первом запросе скачивает модель из интернета и падала без сети; заменен на легкий поиск без внешних зависимостей
  по `agent/knowledge/` (добавлены примеры материалов).
- **Сборка**: в фронтенде не было корневого `tsconfig.json` (`npm run build` не запускался), не было Dockerfile; добавлены Dockerfile'ы,
  общий `docker-compose.yml`, healthcheck'и. Из бэкенда убран `.env` с локальными адресами, из `package.json`/зависимостей агента лишнее.
- **Мелочи**: добавлены `GET /patient/measurements/latest` (последний замер для главной после перезагрузки) и время приема в `treatment-plan`;
  убраны выдуманные данные с главной (118/76, «Под контролем», «в 20:00»); обработка ошибок записи (409), страница «Лечение» с расписанием.

## Известные ограничения

- Входа пользователей нет: JWT выдается демо-пациенту по `patient_id` (`ENABLE_DEV_TOKEN=true`). Для продакшена нужна настоящая авторизация.
- Страницы «Аналитика», «Запись» (история) и «Рекомендации» остались заглушками: под них нет эндпоинтов бэкенда.
- Менеджер WebSocket хранит соединения в памяти: бэкенд запускается одним процессом (без `--workers N`).
- Материалы в `agent/knowledge/` демонстрационные, перед реальным использованием их должен утвердить врач.
